# Internationalization (i18n)

The workspace ships with shared English and Russian translations for frontend copy and backend problem responses. The goal is to keep user-facing text localizable while preserving stable error codes for clients, logs, and alerting.

## Locale catalog placement

Locale JSON catalogs live at the repository root as thin scoped files under `i18n/<locale>/<scope>/<component>.json`. Keep catalog assets outside compiled libraries. The exported `supportedLocales` tuple and `defaultLocale` value in `@app/common-i18n-runtime` are the single source of truth for supported and default locales; runtime code, validation, persistence defaults, bot setup, and tooling must consume them instead of declaring local copies. Do not create unrelated package-root locale directories.

This document deliberately does not list the supported locales. A prose copy of
that list is a duplicate that drifts the moment a locale is added — read
`supportedLocales`, or `ls i18n/`, for the current set.

Only platform-neutral mechanics stay under `libs/common/i18n`: `@app/common-i18n-runtime` owns the tuple-derived `Locale`/`Language` types, runtime `Language` values, `getLocalization`, locale parsing, merge, fallback, interpolation, and catalog translation; `@app/common-i18n-keys` owns generated key types. Backend request/error catalogs live in `@app/backend-common-i18n`. Frontend shared catalogs live in `@app/frontend-i18n-shared`, while admin/user/landing loaders live directly in their frontend feature i18n libraries. Telegram and Discord merge bot assets inside their owning backend features.

Catalog scopes are ownership boundaries:

- `i18n/<locale>/common/shared.json` for shared UI, runtime overlay, language, theme, and common status copy.
- `i18n/<locale>/common/errors.json` for shared API/problem/validation fallback copy.
- `i18n/<locale>/landing/app.json` for the landing frontend.
- `i18n/<locale>/admin/*.json` for admin frontend shell and pages.
- `i18n/<locale>/user/*.json` for user frontend shell, auth, social auth, and TMA copy.
- `i18n/<locale>/bots/*.json` for Telegram bot and Discord interaction copy.

Frontend apps pass scoped catalog sets into `FrontendI18nProvider`: landing imports `landingFrontendTranslations` from `@app/frontend-feature-landing-i18n`, user/mobile/site import `userFrontendTranslations` from `@app/frontend-feature-user-i18n`, and admin imports `adminFrontendTranslations` from `@app/frontend-feature-admin-i18n`. These feature libraries own their loader implementation and app-specific assets rather than re-exporting code from a misleading common/frontend tree.

Frontend runtime and API support import `@app/frontend-i18n-shared`. Backend bootstrap, responses, exceptions, and feature DTOs import `@app/backend-common-i18n`. Telegram owns `telegramTranslations`; Discord owns `discordTranslations`; `bots/shared.json` contains only bot copy genuinely consumed by both, and each bot binds its own `bots/<bot>.json` so neither ships the other's copy. There is no aggregate catalog that makes every core API depend on Telegram or Discord assets.

Discord publishes a closed locale vocabulary and rejects an entire bulk command registration when one localization key falls outside it, so `localizationsFor` canonicalizes each workspace locale to BCP 47 and then keeps only the tags `discord-api-types` declares. A locale Discord does not carry is left out of the payload instead of breaking every command, and a registration dry run reports it in `unpublishedLocales`. Set `DISCORD_LOCALE_OVERRIDES` to comma-separated `<workspace locale>=<Discord locale>` pairs — `uz-cyrl=ru` — to publish such a locale under the nearest tag Discord does carry.

The scope list above is the boilerplate's own set, not a closed one. Tooling discovers namespaces from the default locale's tree rather than from a hardcoded list, so a product that adds `i18n/<locale>/marketplace/listings.json` gets the same parity enforcement as a scope shipped here, with no tooling change. What the gates require is that every locale carries the same set of namespaces the default locale does.

A file directly at the locale root — `i18n/<locale>/lint.json` and anything beside it — describes the locale rather than translating it, and is not read as a catalog. The rule is the shape, not the name: a catalog is always `<scope>/<file>.json`, so a product may add its own locale-root metadata without it being reported as a stray catalog or scanned for translation keys.

The scoped code and locale asset folders are separate buildable Nx projects. Changing `i18n/en/user/auth.json` affects user-owned frontends, changing `i18n/en/admin/users.json` affects admin, and changing `i18n/en/landing/app.json` affects landing. Common files affect backend common and frontend shared catalogs; bot assets affect only Telegram/Discord feature graphs.

## Locale detection and persistence order

Backend request locale resolution uses the first supported locale found in this order:

1. `?lang=` or `?locale=` query parameter
2. `x-locale` or `x-language` header
3. `locale` or `lang` cookie
4. `Accept-Language` header
5. Shared `defaultLocale`

Header names are resolved case-insensitively, so Node/Fastify's lowercase `accept-language`, the HTTP spelling `Accept-Language`, and Fetch-compatible `Headers` all use the same shared resolver. `Accept-Language` supports weighted language ranges, regional values such as `ru-RU`, and the shared default when no supported range matches. Backend code that needs the selected API language must use `resolveLanguageFromHeaders` or `resolveLanguageFromRequest` from the shared/backend i18n API instead of parsing header substrings locally.

Authenticated frontend sessions additionally persist profile preferences in `auth_users.locale` and `auth_users.theme`. Locale remains constrained to `supportedLocales` when present. Theme is constrained to `system`, `light`, or `dark`, and defaults to `system` for existing and new users. After authentication is available, the session-authenticated user and admin frontends load `/auth/me` and/or profile data, apply saved locale/theme first, then continue using browser-safe fallback behavior if no saved preference exists:

1. saved authenticated user locale from `/auth/me` or profile data
2. `?lang=` or `?locale=` query parameter
3. `boilerplate.locale` in `localStorage`
4. `locale` or `lang` cookie
5. `navigator.languages` / `navigator.language`
6. Shared `defaultLocale`

Guests use only browser-safe fallback behavior from URL/localStorage/cookie/browser/default values.

The frontend language switcher always persists locale locally in `localStorage` and a `locale` cookie. The theme switcher persists `boilerplate.theme` in `localStorage`, sets `document.documentElement.dataset.themePreference` to `system|light|dark`, and sets `document.documentElement.dataset.theme` to the resolved `light|dark` value. System-theme preference tracks `prefers-color-scheme` changes and applies updates live.

For authenticated users, language/theme switches call the generated `authApi.authControllerUpdatePreferences` wrapper for `PATCH /auth/me/preferences` so both preferences follow future sessions. `PATCH /auth/me/locale` remains as a compatibility wrapper that routes through the same preference update path. User and admin frontend API calls must always send `Accept-Language` with the current resolved locale; backend APIs still localize each request from that frontend-provided header (or the backend fallback chain above).

## Auth preferences API

The auth preference contract is intentionally partial-update friendly:

```json
{
  "locale": "en",
  "theme": "system"
}
```

Both fields are optional on `PATCH /auth/me/preferences`. Omitted values are preserved, unsupported locale or theme values return a localized 400 problem response, and successful updates return the updated authenticated user view. `GET /auth/me`, auth session DTOs, and frontend generated auth types include `theme` alongside `locale` so app/admin shells can hydrate preferences without a second preferences-specific request.

When changing preference fields or validation rules:

1. Update backend DTOs, views, persistence records, and MikroORM migrations first.
2. Regenerate OpenAPI contracts and generated frontend clients.
3. Update the typed wrappers/hooks in `libs/frontend/api-client/lib/src/auth.ts`.
4. Add tests for valid updates, invalid values, defaults, persistence, compatibility routes, and frontend guest/auth behavior.

## Frontend request, server-state, and shell-state management

The user and admin React apps use TanStack Query for backend request/server state: cacheable reads, mutations, retries, invalidation, and loading/error lifecycles. Do not move server-fetched user/profile/list data into MobX; keep it in TanStack Query so request ownership remains explicit.

MobX is included as the client/UI shell state foundation in `@app/frontend-runtime`. The shared `RootStore` owns `AppStore` (app status, viewport width, and breakpoint shell state), `LocaleStore`, `AuthShellStore`, and `UiStore` for observable client-only state such as active locale/theme, session-status hints, sidebar/modal state, and future shell state. Credentials remain exclusively in the server-managed HttpOnly session cookie. React local state is still appropriate for small, purely local transient details such as one form field, route snapshots, authenticated preference overrides, or an uncontrolled disclosure.

All frontend backend calls must go through `apiFetch` from `@app/frontend-api-support` or the generated `@app/frontend-api-client` wrappers that use API support; do not call raw `fetch` from non-test app or shared frontend source outside the API-support implementation. App providers bridge the current runtime locale into API support, and `apiFetch` sends the HttpOnly session cookie and injects `Accept-Language` at request time with the JSON headers. This ensures locale changes affect the next request without duplicating header logic in feature components. API support also localizes its fallback request-failed copy from the current API locale when a problem response does not include localized text.

When adding a backend call:

1. Add or regenerate the typed client wrapper in `@app/frontend-api-client` rather than embedding endpoint paths in app code.
2. Use `useQuery` for reads and include stable query-key parts such as domain, resource, session scope, and `locale` when localized response data can change.
3. Use `useMutation` for writes, then invalidate affected query-key prefixes with `queryClient.invalidateQueries`.
4. Let `@app/frontend-api-support` own cookie credentials, `Accept`, `Accept-Language`, `Content-Type`, URL resolution, and localized fallback request-failed copy.
5. Add or update tests for headers, query invalidation behavior, generated wrapper use, and the raw-fetch guard.

## Adding a locale or key

Translation assets live in root `i18n/<locale>/<scope>/<component>.json`; key types and runtime mechanics live under `libs/common/i18n/{keys,runtime}`; backend common catalog code lives under `libs/backend/common/i18n`; frontend shared catalog code lives under `libs/frontend/i18n/shared`; and app-owned loaders live under `libs/frontend/feature/<scope>/i18n`.

1. Add the locale to `supportedLocales` in `libs/common/i18n/runtime/lib/src/runtime.ts`; `Locale` is derived from that tuple. Change `defaultLocale` there only when the product default changes.
2. Mirror the default locale's `i18n/<default>/` tree into `i18n/<locale>/`: every scope directory (`common`, `landing`, `admin`, `user`, `bots`) and every catalog inside it. The thin locale catalog guard in `pnpm run tooling:static-check` takes that required set from the default locale, so it reports whatever is missing or unexpected.
3. Add every new key to every locale catalog. The `TranslationKey` union is derived from the catalog tree, not maintained by hand.
4. Declare the locale's prose rules in `i18n/<locale>/lint.json`. The file is required for every non-default locale; see [Locale prose rules](#locale-prose-rules) below.
5. Run `pnpm run i18n:catalogs` to regenerate every artifact derived from the locale axis: the per-consumer `catalogs.generated.ts` bindings — backend common, the Telegram and Discord bots, and the shared/landing/admin/user frontends — and the `TranslationKey` union. Both carry a generated header and must not be edited by hand; `pnpm run i18n:catalogs:check` reports drift and blocks the PR lane. No binding module is edited by hand for a locale; the only hand-maintained axis is which catalogs a consumer binds, in `localeCatalogBindings`.
6. Place keys in the matching scoped component file (`landing/app.json`, `admin/users.json`, `common/errors.json`, `user/social-auth.json`, `bots/telegram.json`, and so on). Keep each file at or below 60 keys and 90 non-empty lines; split large domains before exceeding those limits.
7. Keep keys stable and descriptive, for example `landing.title`, `common.language`, `common.theme.dark`, or `errors.bad-request.title`. Landing/user/admin user-facing copy must use keys for visible text, aria labels, placeholders, fallback errors, card/stat labels, title strings, and shared UI defaults. The shared `no-hardcoded-copy` guard catches practical JSX/prop/property regressions.
8. Add tests for locale resolution, interpolation, fallback behavior, runtime and scoped frontend catalog parity, duplicate raw/merged key detection, thin-file policy, affected-project isolation, and any new domain-specific keys.
9. Leave the language switcher alone. Its labels come from `localeLabel`, which renders the locale through `Intl.DisplayNames` and degrades to the canonical BCP 47 tag where a runtime ships without display data. A `common.language.<locale>` key is an optional override for a product that wants its own wording — the shipped `en`/`ru` entries are that worked example — and never a requirement, which is what keeps a locale addition off the N x N grid of a label per locale in every catalog. Update theme-adjacent labels only if the preference UI changes.

Missing keys fall back to the default locale before returning the key name, which makes gaps visible during development without crashing production pages.

## Locale prose rules

Key parity and placeholder parity both pass on a catalog that was never translated: the keys are present and the placeholders match because the values are still English. Each non-default locale therefore declares what "still English" means for it in `i18n/<locale>/lint.json`, which the thin locale catalog guard in `pnpm run tooling:static-check` enforces. The file is required — an absent declaration is reported rather than treated as "nothing to check" — and an empty `{}` is a valid starting point that already enforces the identical-to-fallback rule.

| Field                    | Effect                                                                                                                                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `residuePatterns`        | `{ "pattern", "label" }` entries compiled as unicode regular expressions. A match reports the key with the declared label. Use them for letters or spellings that prove the string came from another locale. |
| `foreignProseMarkers`    | Whole words (case-insensitive) whose presence means the value is still source-language prose.                                                                                                                |
| `reviewedTechnicalTerms` | Terms the locale deliberately keeps in their source form. They are removed from the value, longest first, before the other rules read it, so `PostgreSQL` never counts as untranslated prose.                |
| `untranslatedKeys`       | Keys whose value is allowed to be byte-identical to the default locale — brand names, provider names, and placeholder addresses. Every other key that matches the fallback verbatim is reported.             |

Interpolation is removed before any of these rules read a value. Placeholder names are identifiers a developer chose, not copy anyone translates, so `{{error}}` never counts as the marker `error` and a placeholder never makes a Latin-letter residue pattern fire on an otherwise translated string. Declare rules against the prose you can actually see.

Adding an entry to `untranslatedKeys` is a review decision, not a way to silence the gate: prefer translating the value, and reserve the list for copy that genuinely has no translated form. `i18n/ru/lint.json` is the worked example.

## Social auth, TMA, bot, and Discord key conventions

Future social-auth and bot surfaces reserve stable key prefixes so runtime work can stay localized from the start:

- `auth.provider.*` for provider labels such as Telegram and Discord.
- `auth.social.*` for social-auth buttons, link/unlink statuses, callback errors, provider conflicts, step-up prompts, last-method guard copy, and create-account flows.
- `tma.*` for Telegram Mini App loading, unsupported-client, authenticated, account-link, and Mini App deep-navigation states.
- `deepNav.*` for provider-neutral deep-link loading, unsupported, authenticated, link-required, expired, and not-found states.
- `bot.menu.*`, `bot.route.*`, `bot.error.*`, and `bot.message.*` for Telegram bot menus, routes, rate-limit/expiry errors, link/unlink errors, and generic bot responses.
- `discord.commands.*`, `discord.components.*`, and `discord.messages.*` for Discord slash-command labels, command descriptions, command responses, component labels, rate-limit copy, auth-required copy, and link-conflict messages.

Keep provider-specific names under the provider prefix (`discord.commands.link.description`) and shared social-auth behavior under `auth.social.*`; store Discord interaction keys in `bots/discord.json` and web social-auth keys in `user/social-auth.json` respectively. Do not put bot tokens, client secrets, webhook secrets, provider ids, or environment-specific callback URLs in locale catalogs. See `docs/social-auth-bots.md` for the implemented provider architecture, environment variables, and rollout checklist.

## Frontend usage

Wrap React trees in `FrontendStateProvider` near `FrontendQueryProvider`, then use `FrontendI18nProvider` and `useI18n()` for translations and preference controls:

```tsx
<FrontendStateProvider>
  <FrontendI18nProvider>
    <Page />
  </FrontendI18nProvider>
</FrontendStateProvider>;

const { locale, setLocale, theme, setTheme, t } = useI18n();

setTheme('dark');
return <h1>{t('landing.title')}</h1>;
```

`ProductShell` includes `LanguageSwitcher` and `ThemeSwitcher`, so the landing, user, and admin apps get consistent preference controls. Shared UI tests should pass `initialLocale`/`initialTheme` when they need deterministic copy or DOM attributes.

## Backend exceptions and responses

Backend exceptions use RFC 9457 Problem Details with `type`, `status`, `title`, optional `detail`, optional `instance`, and documented type-specific extensions. The wire media type is `application/problem+json`. Generic errors use `about:blank`; product types use `https://<root-domain>/problems#<code>` identities whose `/problems` resource documents the type. Localization replaces human-readable `title`, `detail`, and validation issue text and declares the selected `Content-Language`; it never changes `type`, `code`, `status`, `instance`, or validation pointers. Frontend API support preserves `type` as the canonical RFC identity and exposes the documented short alias as `code`, with `http.<status>` as the generic fallback.

Use `BaseException` / `Exception` helpers for application errors:

```ts
throw new ForbiddenException({ meta: { permission: 'users.read' } });
```

Problem response filters and result mappers resolve the request locale and localize known error codes such as `bad-request`, `forbidden`, `not-found`, `conflict`, `client-data-validation`, `rate-limited`, `step-up-required`, `last-auth-method-unlink-forbidden`, and `internal-server-error`.

## Validation and rate limits

Validation pipes normalize class-validator failures into localized Problem Details. The problem code remains stable (`client-data-validation`) while field messages can be localized and interpolated. Validation issues are exposed through the `errors[]` extension with per-field `detail` and JSON Pointer `pointer` entries. Rate limit responses use the same problem format and localize the `rate-limited` title/detail.

## Production notes

- Keep problem type URIs and documented error codes stable across releases; changing either is a client contract change.
- Prefer short backend details that are safe to expose to end users.
- Do not put secrets, tokens, or environment-specific values in translation files.
- Add monitoring around error `type`, `code`, and `status`, not localized text.
- Include every supported locale and theme preference in smoke tests for critical auth, profile, and admin flows.
